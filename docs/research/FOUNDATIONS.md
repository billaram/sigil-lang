# Sigil: Research Foundations

## Theoretical Pillars

Sigil stands on five theoretical pillars, each drawn from decades of research.

---

## Pillar 1: Neuro-Symbolic AI

### The Kautz Taxonomy (AAAI 2020)

Henry Kautz proposed six types of neuro-symbolic integration, in increasing order of coupling:

| Type | Pattern | Example | Sigil Alignment |
|------|---------|---------|----------------|
| 1 | Standard neural | BERT, GPT | N/A |
| 2 | Symbolic[Neural] | AlphaGo, AlphaGeometry | **Primary** |
| 3 | Neural\|Symbolic | Neural program synthesis | **Primary** |
| 4 | Neural ∪ Compile(Symbolic) | KBANN | Future |
| 5 | Neural_{Symbolic} | DeepProbLog, LTN | Future |
| 6 | Neural[Symbolic] | Does not yet exist | Vision |

**Sigil operates at Type 2-3**: Neural perception (LLM parsing) feeds symbolic execution (rule engine). This is the same pattern used by AlphaGeometry and AlphaProof — the most successful neuro-symbolic systems to date.

### DARPA Three Waves of AI

| Wave | Era | Capability | Sigil's Position |
|------|-----|-----------|-----------------|
| Wave 1 | 1960s-90s | Handcrafted symbolic reasoning | Symbolic execution engine |
| Wave 2 | 2010s+ | Statistical learning (deep learning) | Neural parser, neural bridge |
| Wave 3 | Emerging | Contextual adaptation (hybrid) | **Sigil itself** |

### Landmark Systems

**AlphaGeometry** (Nature 2024): Neural language model provides geometric construction suggestions; symbolic deduction engine performs rigorous proof search. Solved 25/30 Olympiad-level geometry problems. Validates the neural-intuition → symbolic-verification pattern.

**AlphaProof** (DeepMind 2024): Gemini + AlphaZero RL + Lean 4 formal verification. IMO silver medal. Proves that neuro-symbolic systems can achieve superhuman mathematical reasoning.

**Scallop** (PLDI 2023): Purpose-built neuro-symbolic DSL based on Datalog with provenance semirings. Enables differentiable symbolic reasoning. The closest existing work to Sigil's vision, but focused on differentiable reasoning rather than general-purpose programming.

### Key Papers

1. **Garcez et al. (2017)** — "Neural-Symbolic Learning and Reasoning: A Survey and Interpretation" — 58-page survey establishing the field's taxonomy
2. **Kautz (2020)** — "The Third AI Summer" (AAAI presidential address) — The six-type taxonomy

## Pillar 2: LISP and Symbolic Computation

### Why LISP Matters for Sigil

LISP (1958) introduced three ideas that are directly relevant to Sigil:

**Homoiconicity** — Code and data share the same representation. In LISP, programs are lists. In Sigil, programs are inspectable ASTs that can be manipulated, analyzed, and generated by both humans and LLMs.

**Symbolic Computation** — LISP was built for manipulating symbols, not just numbers. Rules, constraints, and logical expressions are fundamentally symbolic operations. Sigil inherits this orientation.

**Code-as-Data (Metaprogramming)** — LISP macros transform code at compile time. Sigil's two-layer design (surface NL → core S-expression) enables similar metaprogramming: LLMs generate surface code, tooling manipulates core code.

### The Connection to Modern AI

A 2025 paper (arXiv:2506.10021) argues that LISP's homoiconicity makes it ideal for LLM-integrated metaprogramming loops. The paper demonstrates "persistent metaprogramming" where LLMs generate and transform LISP code iteratively.

Sigil takes this further: instead of requiring users to write S-expressions, Sigil provides a natural language surface that *desugars to* S-expressions. The LLM generates readable code; the interpreter works with manipulable symbolic structures.

### Design Decisions Inspired by LISP

| LISP Feature | Sigil Adaptation |
|-------------|-----------------|
| S-expressions | Core AST layer (hidden from surface syntax) |
| `quote` / `eval` | First-class rule values, dynamic rule evaluation |
| Macros | Surface → Core desugaring, future: user-defined syntax |
| Dynamic typing | Gradual typing (optional annotations, inferred where possible) |
| REPL | Interactive Sigil shell with trace visualization |
| Symbolic atoms | Sigil `:keywords` (symbols) |

## Pillar 3: Functional Programming

### Core Principles Applied

| FP Principle | Sigil Application | Rationale |
|-------------|-------------------|-----------|
| **Immutability** | Facts and rules are immutable by default | Deterministic evaluation, safe parallelism |
| **Pure functions** | Compute blocks are pure by default | Referential transparency, testability |
| **Pattern matching** | Rule conditions as pattern matches | Exhaustive, declarative condition evaluation |
| **Algebraic data types** | Sigil type system (sum + product types) | Type-safe domain modeling |
| **Higher-order functions** | Pipeline operator, rule combinators | Composable abstractions |
| **Declarative style** | Rules declare what, not how | Natural for domain experts |

### Lean 4: The Convergence Point

Lean 4 represents the most complete fusion of functional programming and AI:
- Won 2025 ACM SIGPLAN PL Software Award
- Used by AlphaProof as the formal verification backend
- 210,000+ formalized theorems in mathlib
- DeepSeek-Prover-V2 specifically targets Lean 4

Lean 4 demonstrates that a language with dependent types, pattern matching, and algebraic data types can serve simultaneously as a programming language, a proof language, and a target for AI-generated formal reasoning. Sigil draws inspiration from Lean's approach but optimizes for accessibility (natural language surface) over formality (dependent types).

### Haskell's Influence

- Type classes → Sigil's constraint system
- `where` clauses → Sigil's `given ... as ...` bindings
- Guards → Sigil's `when` conditions
- Lazy evaluation → Future: demand-driven rule evaluation
- Monadic I/O → Sigil's explicit `neural` boundary for effects

## Pillar 4: Natural Language Programming

### Historical Lessons

| Language | Year | What Worked | What Didn't |
|----------|------|------------|-------------|
| **Inform 7** | 2006 | Constrained NL within a clear domain; readable and writable by non-programmers | Limited to interactive fiction; scaling issues |
| **AppleScript** | 1993 | English-like syntax is initially appealing | Ambiguity in practice; rigid syntax that merely *looks* like English |
| **Wolfram Language** | 1988+ | NL as input layer translating to symbolic computation | Proprietary; ecosystem lock-in |
| **COBOL** | 1959 | Business-readable syntax | Verbose; NL readability didn't improve maintainability |

### Key Insight: The Wolfram Pattern

Stephen Wolfram argued (2010) that NL programming would succeed by translating to a well-defined computational language — not by making the language itself natural language. This is exactly Sigil's approach:

```
Natural Language (input) → Neural Parser → Sigil (formal language) → Execution
```

The NL is the *input*, not the *language*. Sigil is a formal language with constrained NL syntax — readable like English, parseable like a PEG.

### Inform 7: The Closest Analog

Inform 7 proved that constrained NL can be a real programming language for a specific domain. Example:

```inform7
The Lab is a room. The table is in the Lab.
The beaker is on the table. The beaker is a container.
Instead of taking the beaker when the beaker contains the acid:
    say "The beaker is too dangerous to pick up!"
```

This compiles and executes. Sigil applies the same principle to decision logic and rule systems.

## Pillar 5: Compiler & Language Design

### Parser Technology

**PEG (Parsing Expression Grammars)**: Sigil uses PEG because:
- Unambiguous by construction (ordered choice)
- Linear-time via packrat memoization
- Natural for keyword-heavy DSLs
- Composable and extensible

**Alternative considered**: CFG + LR/LALR. Rejected because ambiguity resolution is manual, and Sigil's NL-style keywords create frequent conflicts in traditional parsers.

### AI-Friendly Grammar Design

Research from MoonBit (ICSE/LLM4Code 2024) and SimPy (ICSE 2024) identifies key properties:

1. **Flat structure**: Minimal nesting → more predictable token generation
2. **Explicit types at boundaries**: Reduces LLM hallucination
3. **Regular syntax**: Consistent patterns → efficient tokenization
4. **Small keyword vocabulary**: Fewer tokens per construct
5. **Deterministic parsing**: Unambiguous grammar → reliable LLM generation

Sigil's grammar is designed with all five properties. The constrained NL syntax adds a sixth: **semantic transparency** — keywords like `when`, `then`, `exceeds` carry their natural meaning.

### Implementation Strategy

Following established best practices:

1. **Phase 1**: Tree-walking interpreter (rapid iteration, easy debugging)
2. **Phase 2**: Optimization passes on AST (constant folding, dead rule elimination)
3. **Phase 3**: Rust core for hot paths (constraint solving, pattern matching)
4. **Future**: Bytecode VM → LLVM backend → native compilation

This is the same path taken by Python (tree-walking → bytecode), Ruby (tree-walking → YARV), and Lua (tree-walking → bytecode → LuaJIT).

### Reference Implementations Studied

| Language | Approach | Lesson for Sigil |
|---------|---------|-----------------|
| **Crafting Interpreters** (Lox) | Tree-walking → bytecode VM | Implementation pattern |
| **Python** | Bytecode VM (CPython) | Indentation parsing, REPL design |
| **Lua** | Register-based VM | Lightweight embedding |
| **Clojure** | Hosted on JVM, reader macros | Interop design, homoiconicity |
| **Zig** | C interop, comptime | FFI design, zero-cost abstractions |
| **Lean 4** | Dependent types, tactic framework | Formal reasoning integration |
| **Scallop** | Datalog + provenance semirings | Neuro-symbolic DSL design |
| **MoonBit** | AI-native, multi-backend | Grammar design for LLM generation |
